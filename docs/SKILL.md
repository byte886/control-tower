# 多仓库体系编排（control-tower）

> 解决一个具体问题：**多个仓库构成一个业务体系时，关系、调度、总控放哪里**。已实践验证于"鉴藏（heritage）体系"五仓：采集底座 content-pipeline / 调研方法论 research-toolkit / 情报雷达 trend-radar / 生产执行 video-studio / 运营分发 we-media-ops。

## 1. 核心原则：意图与驱动分离（最重要）

**错误做法**：总控挂在一个"龙头"仓（如运营仓），所有模块等龙头发指令 → **串行依赖，无法独立测试**。

**正确做法**：把"方向"和"运行"拆成两层，人只管方向、系统自己会转：

| 层 | 管什么 | 谁驱动 | 更新频率 | 载体 |
|---|---|---|---|---|
| **意图层** | 业务方向：做什么领域/选题/优先级/排期 | 人（用户拍板） | 方向变更时 | 策略文档（如 `SYSTEM_STRATEGY.md`）放运营/业务仓 |
| **驱动层** | 运行机制：驱动点/产物对接/任务路由/纪律 | 系统自治（AI + 定时） | 机制变更时 | 架构文档（如 `SYSTEM_ARCHITECTURE.md`）放底座/数据仓 |

- 意图层**异步、不阻塞**：方向可以慢慢定，各仓按自己的驱动点照常跑
- 驱动层**自治、可测试**：每仓有最小闭环（给输入即产输出），独立开发、独立验证

## 2. 产物驱动，而非指令驱动（关键机制）

各仓之间**只通过产物对接**（文件/文档/成品），**不通过上游指令**：

```
上游产物"就绪" → 下游即可消费
（不等待、不轮询、不发指令）
```

每仓定义三件事：**输入（可独立造）→ 自测输出 → 下游消费方**。例如：

| 仓 | 输入 | 自测输出 | 下游消费 |
|---|---|---|---|
| 采集底座 | 一个渠道/博主 | 知识成品 md | 生产取素材、监控取线索 |
| 情报雷达 | 一个主题 | 情报速递 md | 运营选题、生产决策 |
| 生产执行 | 一张产品图 | 成片/方案图 | 运营发布 |
| 运营分发 | 一个选题 | 文案+排期 | 对外发布（无下游） |

**测试独立性**：每个仓拿自己的样例输入（样例博主/样例产品图/样例主题）就能跑通最小闭环，互不阻塞。

## 3. 总控落位决策表

| 情况 | 总控放哪 |
|---|---|
| 有明确"数据源头"仓（采集/底座） | 驱动层文档放底座仓；意图层文档放运营/业务仓 |
| 无底座仓，平级多仓 | 驱动层独立成文（可放任一仓 docs/），明确指针 |
| 体系庞大（>6 仓）| 考虑独立总控仓（但先问：是不是真需要第六个仓） |
| 新业务开仓 | 先定层级归属（采集/调研/监控/生产/运营），再决定放哪层 |

## 4. 任务路由表（接到任务先判断）

```
接到任务 → 判断任务类型：
├─ 业务意图（发什么/卖什么/定方向）→ 意图层策略文档
├─ 采集/知识生成 → 采集底座（流水线）
├─ 查资料/选工具/行业调研 → 调研方法论技能
├─ 盯动态/定时扫描 → 情报雷达（周/双周/月机制）
├─ 出图/出视频 → 生产执行（SOP + 门禁）
├─ 发布/运营内容 → 运营分发（写作SOP + 质检）
└─ 跨层任务 → 先读架构文档路由，再进对应仓
```

## 5. 跨仓纪律（所有仓统一）

1. **来源四档强制**：已查证（官方一手可回源）/ 经搜索补充（≥2独立源）/ 一方说法 / 未经核实单列——不编造 URL/价格/数据
2. **知识格式统一**：知识成品用 OKF v0.2 标准档 frontmatter（各仓 AGENTS 声明 type 词表 + 校验纪律）；存量不强制回填、新写自然采用
3. **仓库命名**：体系级仓库名统一用英文（或拼音），不含旧领域名；改名 = GitHub rename + 本地目录 mv + remote set-url + 全部跨仓引用更新（先 grep 摸引用范围）
4. **子模块纪律**：技能类仓库改后必须回父仓库更新指针再 push
5. **定时更新**：按需周/双周/月/事件驱动（规则/工具/渠道变化）

## 6. 落地步骤（新建或重构体系）

1. **盘仓**：列出所有相关仓库，按五层定位（采集/调研/监控/生产/运营）归类；缺层不硬补
2. **定总控**：按 §3 决策表，写 `SYSTEM_ARCHITECTURE.md`（驱动层）与 `SYSTEM_STRATEGY.md`（意图层，如有运营仓）
3. **建产物对接表**：每仓定义输入/自测输出/下游消费方（§2 表），写进架构文档
4. **写路由表**：任务类型 → 对应仓（§4），写进架构文档
5. **同步指针**：每仓 AGENTS 冷启动路径加一行"跨体系任务先读架构/策略文档"
6. **命名统一**：检查仓名是否含旧领域词（如体系升为 heritage 后还叫 jewelry-xxx），按 §5-3 改名
7. **推送**：所有变更分仓 commit + push（子模块仓回父仓库更新指针）

## 7. 与现有技能的关系

- 本技能管**仓与仓之间**的组织；`project-manager` 管**单仓内部**的项目治理（模板/评审/文档）；`okf-wiki` 管**知识成品格式**。三者互补：先用本技能定体系结构，再用 project-manager 治理每仓，用 okf-wiki 统一知识层。
